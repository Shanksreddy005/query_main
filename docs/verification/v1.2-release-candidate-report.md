## 2. The defect this release closes

`# QueryMind — Production Quality Remediation` recorded one open finding: a query ranked by profit
could be narrated as a ranking by sales. The cause was in the summary layer, not the plan or the
engine: the ranking narrative picked the metric to name by looking for a revenue-shaped column in
the result, so the prose said "ranked by total sales" while the figures it quoted were profit values.

Two properties made it worth care rather than a one-line patch. The label is derived from the
result set, so the wrong column looked entirely plausible; and the summary is what users read as the
answer, so a wrong metric name is a false claim about the analysis even when every number in the
result is correct.

## 3. Contract now enforced

The ranked metric is read from the executed query, and the plan is consulted only where the query is
silent:

1. Every ordering term in the statement is collected with its parenthesis depth — the outer clause
   first, then a window function's clause — using quote- and bracket-aware boundaries so a `LIMIT`
   inside a string or a nested call cannot truncate the clause.
2. A term is named only when it maps onto exactly one column the query actually returned: by alias,
   by output position (`ORDER BY 2`), by the source column an aggregate consumed, or by an exact
   expression match. Direction comes from the term itself, ascending where no keyword is written.
3. Only a column the result profile recognises as a numeric measure may be named. Window row
   counters (`ROW_NUMBER() … AS rank`) are excluded, and a clause that leads with a partition key or
   a name is read past to the measure behind it.
4. Where no term resolves to one measure — an ambiguous expression, a sort on a column the result
   does not carry, or no ordering at all — the summary reports the returned values, states why no
   metric is named, and makes no leader, difference or share-of-total claim.
5. The plan's metric is used only when the statement carries no ordering, and never to assert a
   leader.

Ground rules unchanged: the LLM remains a semantic planner, deterministic code owns the analytical
contract, DuckDB-WASM executes locally in the browser, and a verified execution result stays the
only source of truth. `validators.ts`, `sqlEngine.ts` and `aiService.ts` were not modified, and the
existing validation and execution contract suites pass unchanged.

expression). Four further tests pin the resolver contract itself.

  is verified against the real summary engine through tests, not through a deployed page.
- Cross-origin WASM loading from R2, the R2 response headers and the CORS origins — unchanged code
  and unchanged bytes, but still only true for a deployment that has not happened.
- Cloudflare Web Analytics / RUM. The edge-injected beacon is an operator dashboard setting; the
  disablement steps are in the production quality remediation report, and `SECURITY.md` plus the
  telemetry auditor copy stay deliberately unreconciled until the live measurement is repeated.
- Provider round trips. No LLM call was made for this fix; the summary layer is deterministic code,
  and no dataset row or complete result was sent to any provider in this work.
