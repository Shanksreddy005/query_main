# QueryMind v1.2 — Live Production Verification

Measured on 2026-11-19 against the running site `https://querymind.in`, after the approved pushes
(`query_main` → `a49532a`, `query_prod` → `7dcdb25`) and after Cloudflare Pages had deployed the new
commit. This report records what was observed in the browser and over HTTP. It is the source of truth
for the privacy, analytics and egress wording now used in `docs/SECURITY.md`, `docs/PRIVACY.md`,
`docs/ARCHITECTURE.md`, `docs/DEPLOYMENT.md` and the deployment repository README.

Ground rules unchanged: the LLM is a semantic planner, deterministic code owns the analytical
contract, DuckDB-WASM executes locally in the browser, and a verified execution result is the only
source of truth. No source file, test, build config, deployed artifact or Cloudflare setting was
modified during this verification.

## 2. Cold-load network posture

This section records two states observed in one verification session, in the order they were measured,
because they are not the same. The final state is the one the release documentation describes; the
earlier state is kept as a finding, not silently dropped.

**Earlier state — an edge-injected analytics beacon.** In an earlier capture of this same session the
served HTML and the live DOM carried a second, third-party script element from
`https://static.cloudflareinsights.com/beacon.min.js/…`, `window.__cfBeacon` was defined as a
configuration object, and the page made a same-origin `POST /cdn-cgi/rum` ping — all three visible to
hooks installed in the top frame. The pre-release audit had recorded the same markers
([production-quality-remediation-report.md](production-quality-remediation-report.md), section 3). That
is Cloudflare Web Analytics / RUM auto-injection behaviour, which is a dashboard setting, not repository
content: no file in `query_main` or `query_prod` contains the string `cloudflareinsights`.

**Final state — the artifact as deployed.** A reload with the browser cache bypassed, with fetch/XHR and
console hooks installed at document start, produced:

1. the HTML document,
2. `assets/index-BrYHrD16.js`,
3. `assets/index-B5urW9Yt.css`,
4. `fonts/inter-latin-variable.woff2`,
5. `fonts/jetbrains-mono-latin-variable.woff2`,
6. one `blob:` list entry — a same-origin object URL materialised by the app itself, not a network
   origin. The observed set therefore is HTML, JS, CSS and two fonts.

The live `document.scripts` list then contained exactly one entry, the app bundle, and
`window.__cfBeacon` was undefined. Six cache-bypassing `fetch('/?<unique>', {cache:'no-store'})` calls
from the deployed origin each returned 1,790 bytes with exactly one `<script>` element, and a `curl`
request for `https://querymind.in/` from outside the browser returned a document byte-identical to
`query_prod/index.html`. Zero requests to any non-`querymind.in` origin were recorded in that capture,
and before any query was run.

In each cold-load capture taken before any diagnostic request was issued, the only origin in the page
frame's Resource Timing list was `https://querymind.in`; nothing changed after running queries in
keyless mode. The `assets.querymind.in` entries that show up in the same list later in the session
belong to the verification fetches described in section 6, not to application behaviour — the engine's
own binary fetch is issued by the DuckDB worker and is not visible in the page frame's list at all. No
`POST /cdn-cgi/rum` upload was observed in the final captures; the one seen earlier in the session is
recorded above.

**Response headers on the edge.** Measured with `curl` against the deployed document and a hashed asset:
both carry `Server: cloudflare`, `x-content-type-options: nosniff` and `referrer-policy:
strict-origin-when-cross-origin`, and both carry `Nel` / `Report-To` headers naming
`https://a.nel.cloudflare.com/report/v4` with `"success_fraction": 0.0` and `max_age` 604800 — Cloudflare
Network Error Logging, which lets a browser report *failed* connections on this host to Cloudflare. It was
not exercised and no such report was observed; it is recorded because it is a channel this application
does not control. `http://querymind.in/` answered `301` to `https://querymind.in/`. Neither response
carried `Strict-Transport-Security`, a Content-Security-Policy (header or `meta`), `X-Frame-Options` /
frame-ancestors, or a `Permissions-Policy`. The HTML is served `Cache-Control: public, max-age=0,
must-revalidate` and the hashed asset `public, max-age=14400, must-revalidate`. All of this is hosting
behaviour, listed here so the security document's claims about it stay factual.

## 3. Analytics and RUM — measured wording

The statements below are the canonical wording other documents point at. Each is scoped to what this
test could actually measure, and none of them is a claim about a Cloudflare dashboard setting.

**No analytics or RUM beacon was detected in the measured application.** In the final state described
in section 2, the served HTML, the live DOM, the text of the shipped bundle and the network log of the
tested cold loads contained none of `cloudflareinsights`, `beacon.min.js`, `__cfBeacon`, `cdn-cgi/rum`,
`gtag`, `googletagmanager`, `fathom` or `plausible`, as markup, as code or as a request. The page had
exactly one script element: the app bundle. The same is true of every QueryMind artifact — the string
appears in no source file, no test, no build configuration and no deployed file, and the repository
artifact `query_prod/index.html` is byte-identical to the document the edge served in this state.

**An earlier capture in the same session did contain the beacon.** Section 2 records the
`static.cloudflareinsights.com` script, the `__cfBeacon` configuration object and the matching same-origin
`POST /cdn-cgi/rum` ping observed before the cache-bypassing reload. This pass cannot attribute the
difference between the two states: it did not inspect the Cloudflare dashboard, did not purge the cache,
and made no configuration change. What the two states have in common, and what is therefore safe to
publish, is that the beacon is not part of QueryMind's own code or artifacts.

**No third-party analytics request was observed in the final cold loads.** In the captures of section 2's
final state, the destinations seen were the Pages origin and, for engine binaries, the operator-owned R2
custom domain described in section 6; the earlier beacon capture above is the exception, and it is
recorded as such. Provider endpoints were not contacted at all, because no provider key was configured.

**An unexplained browser-environment global was present.** A `window.RumSDK` global was observed in the
page context of the automated browser used for this test — an object carrying an `ArmsRum` key and a
`default.client` whose configuration names `perf-collector`, web-vitals, exception, API and
static-resource collectors and an endpoint host under `rum.aliyuncs.com`. It could not be attributed to
QueryMind on the available evidence: the served HTML does not contain the string, the DOM contains no
script element other than the app bundle, the bundle text contains neither `RumSDK` nor `ArmsRum` nor
that endpoint host, and the page issued no request to it. It was still present after a cache-bypassing
reload in which no third-party script was loaded at all, which is why it is recorded as an environment
observation rather than application code; note that the pre-release audit listed a global of this shape
among the Cloudflare beacon markers, and this pass found the global without the beacon. This test does
not establish what placed it in the page context, and no claim is made that it is caused by the
automation browser or by any other specific source.

**What this does not say.** The earlier audit
([production-quality-remediation-report.md](production-quality-remediation-report.md), section 3)
recorded an edge-injected analytics beacon on this site, and section 2 above observed one again in part
of this session. Because no Cloudflare dashboard was opened or inspected, nothing in this report
establishes that any Web Analytics or RUM setting is enabled or disabled; it establishes only what
appeared, or did not appear, in the responses and traffic measured here. Until the dashboard itself is
checked, the site's beacon state must be described as **not under repository control and not
definitively measured**, and `docs/SECURITY.md`, `docs/PRIVACY.md` and `docs/ARCHITECTURE.md` say so.

## 6. Engine binaries: R2 headers and CORS

The shipped bundle contains exactly one engine-binary base, `` `https://assets.querymind.in/duckdb/${gu}` ``,
with the pinned version `1.33.1-dev57.0`. The Pages origin cannot serve these files: a request for
`/duckdb/duckdb-eh.wasm` on `querymind.in` returns the single-page HTML fallback with `Content-Type:
text/html`, not a binary. The engine therefore runs from the R2 objects, and it does run — every query
above executed against a live worker.

From the deployed origin, in the browser:

| Object | Status | `Content-Type` | Bytes read | `Cache-Control` |
|---|---|---|---|---|
| `duckdb/1.33.1-dev57.0/duckdb-eh.wasm` | 200 | `application/wasm` | 35,913,747, magic `\0asm` | `public, max-age=31536000, immutable` |
| `duckdb/1.33.1-dev57.0/duckdb-mvp.wasm` | 200 | `application/wasm` | 41,325,187, magic `\0asm` | `public, max-age=31536000, immutable` |

Both fetches completed with a CORS-satisfied response type from the `https://querymind.in` origin, and
the byte counts match the release inventory exactly. Complementary HTTP-level checks made in the same
pass: an `Origin` header for the deployed site is echoed in `Access-Control-Allow-Origin`, an
unapproved origin (`https://evil.example`) receives no such header at all, and an `OPTIONS` preflight
declaring only `Access-Control-Request-Method: GET` answers `204` with
`Access-Control-Allow-Methods: GET` and `Access-Control-Max-Age: 86400`. Listing the bucket itself
returns `404`, so only the custom domain serves the objects.

One CORS detail is worth recording for whoever operates the bucket next. The objects themselves do serve
byte ranges to a client that is not doing a cross-origin browser read: a `Range: bytes=0-1` request
answers `206` with `Content-Range: bytes 0-1/35913747` and the object advertises `Accept-Ranges: bytes`.
But a browser preflight that also declares `Access-Control-Request-Headers: range` is answered `403
Forbidden` with no `Access-Control-*` headers — the rule set allows the method and not that header. The
practical effect is that a cross-origin range request from a page on `querymind.in` would fail, and the
application never issues one: the engine asks for the whole module with a plain `GET`, which succeeds as
shown above. The first time this pass saw two `Access-Control-Allow-Origin` CORS errors in the console it
was this diagnostic fetch causing them, not the application; a fresh reload with the same hooks produced
zero. No R2 object, header or CORS setting was changed, and closing this observation would be a bucket
configuration change requiring its own approval.

## 7. Chart and data exports

"Download Chart as SVG" on a live chart produced `querymind_chart_<timestamp>.svg`, 4,925 bytes,
`image/svg+xml`. The file declares its own XML prolog, `xmlns`, `width="880"`, `height="520"` and a
matching `viewBox`; it carries `<title>`, `<desc>` and `aria-label` naming the chart ("Leading Product
in Each Region (Total Units Sold)"), 17 text elements including both axis captions and per-bar value
labels, and 22 inline `fill` attributes. It contains no `class` attribute, no `<link>`, no `<style>`, no
`@import` and no external `url()` reference. Loaded as a standalone image it reported intrinsic
dimensions of 880 × 520 and rasterized with every pixel painted, which is the behaviour the SVG fix was
made to produce.

Bonus checks in the same session: the CSV export produced 283 bytes of correct rows and header, and the
JSON export produced 1,605 bytes carrying the question and the executed SQL.

## 8. Console behaviour

Cold load, and every verified-sample run described above, produced **zero console errors and zero
warnings**. The only error-level output observed in this pass came from the missing-key contract guard:

```
Query execution error: Error: An AI API Key (Google Gemini, Groq, or OpenAI) is required to analyze
arbitrary natural language queries like "Top products by total profit". Please open Settings …
```

Two occurrences were logged, one per rejected question, both for free-text questions outside the
verified-sample set submitted with no provider key configured. The rejection itself is correct and
intended: the guard refuses to guess an analytical contract it cannot plan or validate, and the UI
simultaneously showed the matching notice with an "Open Settings" action instead of a result. These are
not failed demo queries and not wrong answers. They are recorded here because the checklist phrase "no
console errors" would otherwise read as absolute: on the deployed build, each keyless rejection of an
unsupported free-text question also writes a `console.error` line with a stack trace. Making that an
expected, non-error log entry is a source-code change and is deliberately out of scope for this
documentation pass.

## 9. Not verified in this pass

- A real provider round trip: no API key was entered, so "Test Key" success and invalid-key provider
  error rendering were not exercised against a live provider.
- The state of any Cloudflare Web Analytics or RUM dashboard setting; none was inspected. This pass
  therefore cannot explain why the beacon appeared in one capture and not in the ones that followed, and
  it cannot say the feature is off.
- What placed the `window.RumSDK` global in the page context of the test browser.
- Whether Cloudflare Network Error Logging ever delivered a report from a visitor's browser; the
  `Nel` / `Report-To` headers were read, the channel was not exercised.
- `www.querymind.in`, which did not resolve when queried (`curl: (6) Could not resolve host`), and the
  Pages `*.pages.dev` preview origin. Only the apex origin was measured, and only in one browser
  automation profile.
- Cross-browser, mobile-viewport and reduced-motion behaviour, and a full accessibility review. One
  known cosmetic nit remains open from the earlier audit: below the 640 px breakpoint the icon-only
  upload button carries no accessible name.
- Sustained load, long-session stability and memory behaviour of the engine.
- Legal or compliance conclusions. Nothing in this report should be read as a certification claim.
